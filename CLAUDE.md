## Overview

This repository contains OPA (Open Policy Agent) Rego policies auto-generated by Permit.io for the `banana-fram` project. The policies implement a multi-model authorization system supporting RBAC (Role-Based Access Control), ABAC (Attribute-Based Access Control), and ReBAC (Relationship-Based Access Control).

## Repository Structure

### Core Policy Files (Root Level)
- **root.rego**: Top-level policy entry point that orchestrates between Permit-generated policies and custom policies
- **abac.rego, rbac.rego, rebac.rego**: Root-level policy implementations for each authorization model
- **user_permissions.rego**: Aggregates permissions across all three models (RBAC, ABAC, ReBAC) for a given user
- **authorized_users.rego**: Returns all users authorized to perform an action on a resource
- **bulk.rego**: Handles bulk authorization checks by iterating over multiple checks
- **any_tenant.rego**: Evaluates which tenants a user has access to based on their assignments

### Directory Structure


### The .manifest File
The `.manifest` file at the root defines the load order for policy files. When the policy bundle is evaluated, files are loaded in the order specified in this manifest to ensure proper dependency resolution.

## Policy Architecture

### Authorization Flow
1. **Entry Point**: `permit.root` package (root.rego)
   - Evaluates both `permit.policies.allow` (generated) and `permit.custom.allow` (user-defined)
   - Returns `allow = true` if EITHER condition passes (OR logic)
   - Tracks which source allowed the decision via `allowing_sources`

2. **Multi-Model Evaluation**: `permit.policies` package (permit/root.rego)
   - Attempts authorization through RBAC, ABAC, and ReBAC in parallel
   - Returns `allow = true` if ANY model allows (OR logic)
   - Tracks which model(s) allowed via `__allow_sources`

3. **Model-Specific Logic**:
   - **RBAC**: Direct role assignments on tenants (`data.users[user].roleAssignments[tenant]`)
   - **ReBAC**: Relationship-based roles derived via graph traversal (calls `permit_rebac_roles` built-in)
   - **ABAC**: Attribute-based conditions evaluated through condition sets

### Key Concepts

#### Condition Sets (ABAC)
- User sets and resource sets are defined in `permit/generated/conditionset/`
- File names are URL-encoded (e.g., `_5f_5fautogen_5fadmin.rego` = `__autogen_admin`)
- Evaluated against `data.condition_set_rules` to determine permissions
- Can be based on user/resource attributes or simple type matching

#### Tenants
- Multi-tenant isolation is built into the policy structure
- Tenant key format: `__tenant:<tenant_id>`
- Role assignments are scoped to tenants
- The special type `__tenant` represents tenant-level resources

#### ReBAC Integration
- Calls external built-in function `permit_rebac_roles` (not defined in Rego)
- Expects `data.role_assignments`, `data.relationships`, `data.resource_types`
- Returns derived roles based on resource relationship graph

#### Debugger
- Controlled by `input.use_debugger` and `data.use_debugger` flags
- When activated, returns detailed decision traces in `debug` output
- Includes model-specific debugging (RBAC, ABAC, ReBAC explanations)

## Working with This Repository

### Branch Convention
- Auto-generated branches follow pattern: `permit/generated/<hash>`
- Main branch: `main`
- Code is generated by Permit.io based on policy configuration in their system

### DO NOT Modify
These files are auto-generated and will be overwritten:
- All files in `permit/generated/`
- All files in `permit/utils/`
- All files in `permit/debug/`
- All files in `permit/placeholders/`
- Root-level policy files: `abac.rego`, `rbac.rego`, `rebac.rego`, `user_permissions.rego`, `authorized_users.rego`, `bulk.rego`, `any_tenant.rego`
- `permit/root.rego`

### Safe to Modify
- `custom/root.rego` - Add custom authorization logic here
- Files you create outside the `permit/` directory

### Testing Policies
To test these policies, you need OPA (Open Policy Agent):
```bash
# Install OPA
brew install opa  # macOS
# or download from https://www.openpolicyagent.org/docs/latest/#running-opa

# Run a simple test
opa eval -d . -i input.json "data.permit.root.allow"

# Run with debugger enabled
opa eval -d . -i input.json "data.permit.root.debug"
```

### Input Format
Expected input structure for authorization checks:
```json
{
  "user": {
    "key": "user@example.com"
  },
  "action": "read",
  "resource": {
    "type": "Document",
    "key": "doc_123",
    "tenant": "tenant_1",
    "attributes": {}
  },
  "context": {
    "use_factdb": true,
    "enable_abac_user_permissions": true,
    "enable_abac_authorized_users": true,
    "optimized": false
  },
  "use_debugger": false
}
```

### Data Format
The policy expects data in the following structure:
- `data.users[user_key]` - User objects with roleAssignments
- `data.tenants[tenant_key]` - Tenant objects
- `data.role_permissions[resource_type][role_key]` - Permission grants by role
- `data.condition_sets[set_key]` - ABAC condition set definitions
- `data.condition_set_rules[user_set][resource_set]` - ABAC permission mappings
- `data.role_assignments["user:<key>"]` - Role assignments by user
- `data.relationships` - ReBAC relationship graph
- `data.resource_instances[resource_key]` - Resource instance data

## Common Queries

### Check if user is allowed
```bash
opa eval -d . -i input.json "data.permit.root.allow"
```

### Get user's permissions on resources
```bash
# Set input.context.enable_abac_user_permissions = true
opa eval -d . -i input.json "data.permit.user_permissions.permissions"
```

### Find authorized users for a resource/action
```bash
# Set input.context.enable_abac_authorized_users = true
opa eval -d . -i input.json "data.permit.authorized_users.authorized_users"
```

### Get all tenants user can access
```bash
opa eval -d . -i input.json "data.permit.any_tenant.allowed_tenants"
```

### Debug a decision
```bash
# Set input.use_debugger = true or data.use_debugger = true
opa eval -d . -i input.json "data.permit.root.debug"
```

## Understanding Changes

When reviewing commits from Permit:
- **Condition set changes**: New files in `permit/generated/conditionset/` indicate new ABAC rules
- **Policy merges**: Updates to core policy files reflect changes in role/permission structure
- **Full policy regeneration**: Complete rewrites indicate major configuration changes in Permit

The commit messages typically indicate the type of change:
- `[Permit code-generation] added new condition set: X` - New ABAC condition
- `[Permit code-generation] full policy` - Complete regeneration
- `[Permit code-generation] merged permit static policies` - Updates to core policy logic
